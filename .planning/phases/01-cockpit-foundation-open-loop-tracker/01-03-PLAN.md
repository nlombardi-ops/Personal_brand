Create `app/api/community/open-loops/[id]/route.ts` exporting a single PATCH handler and no
other verb — Next returns 405 for the rest automatically, and there is deliberately no
removal endpoint on this resource because discarding is a status change, not a deletion

Order inside the handler is fixed: call `requireAuth(request)` as the literal first
statement and return its response when non-null; then wrap `await request.json()` in a
try/catch returning 400 on malformed JSON; then run `validateLoopInput` in non-create mode
so every supplied field is re-checked against the same length caps and enum allow-lists as
create (an edit must not be a way around them); then read the array via `getOpenLoops()`,
find the index by id, return 404 with a not-found error when it is -1, apply the patch,
`saveOpenLoops()`, and return the updated loop. Wrap the store section in try/catch and
return 500 with the repo's standard message shape. Never log the request body.

In `lib/community/loop-defaults.ts` add a module-level frozen allow-list of the keys a PATCH
may touch — title, kind, status, owner, owner_detail, next_action, due — and export an
`applyPatch(existing, patch)` that builds the next object by copying the existing loop and
then reading ONLY those keys from the patch, refreshing `updated_at` to a fresh ISO
timestamp. It must never spread the raw patch object. This single choke point does three
jobs at once: it blocks mass assignment of server-owned fields (id, created_at, source and
every LPH field stay untouchable from the wire), it makes prototype-polluting keys
structurally unreachable because they are not on the allow-list, and it keeps `id` stable so
the stored array cannot be corrupted by a body that renames a record. Do not rely on
filtering dangerous key names — rely on the positive allow-list.

Modify `app/components/community/LoopSlideOver.tsx` to support an edit mode alongside the
create mode it already has. In edit mode the panel title reads "Editar bucle" (create mode
